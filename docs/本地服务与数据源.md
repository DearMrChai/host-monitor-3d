## 七、设备清单落成本地文件（`serve.mjs` + `devices.json` / `zones.json` / `settings.json`）

`file://` 双击打开时浏览器**不能写盘**，所以"编辑同步改配置文件"必须过一次本地 HTTP：
（2026-09-24 之后监控墙这一页连 `file://` 都打不开了 —— 它的代码是真 import 本地 `.mjs` 的，
浏览器不许从 `file://` import 本地模块；双击时状态条会直接写出该跑 `node serve.mjs`。下面这些"没服务时怎样"
的路径现在只对剪影架那一页有效。）

```
cd E:\DSH-workspace\代码仓库\host-monitor-3d
npm i                 → 装 three（校验用）+ ssh2（探测用），只装在本目录
node serve.mjs        → http://127.0.0.1:8123/monitor-wall.html
                        http://127.0.0.1:8123/silhouette-shelf.html
```

- 只监听 `127.0.0.1`，零依赖，静态文件限定在本目录（带目录穿越防护）。
- **两扇门（2026-09-24 需求 #2：把墙分享给 ZeroTier 组里的朋友看）**：来源地址（TCP 那一端报来的，不是 `Origin`）
  分两个名单，环回永远是主人。
  - `HM_ALLOW` = **看**：不给 = 谁能连上谁都能打开这块墙；给了 = 只有名单里的来源打得开页面与任何接口。
  - `HM_OWNER` = **改**：`WRITE_API` 那六条只认这里的名单 —— `POST /api/probe`、`POST /api/round`、
    `GET /api/devices`（这份带明文口令）、`PUT /api/devices`、`PUT /api/zones`、`PUT /api/settings`。
    **不给时回退成 `HM_ALLOW`**，所以老写法（只给 `HM_ALLOW`）升级后不会被锁在自己墙外。
    两句 403 话术各说各的：「只有看板主人能做」= 过了看那道门但没有改的权限；点名 `HM_ALLOW` 的 = 连页面都打不开。
  - 观众读的那份清单是新增的 `GET /api/hosts`：同一份名册，但 `user` / `pass` 两键**整键不出现**（不是置空串），
    另加一格服务端算好的 `live`。为什么必须有 `live`：判据原来是"地址与用户名都填了 = 走 SSH"，
    观众拿不到用户名就算不出这一格，屏上会是一片"模拟"。页面开页先问一次 `GET /api/state`
    （回 `mode: "owner" | "view"`），是观众就隐藏设置入口、清单改读 `/api/hosts`、并且不许把看见的东西反写回去。
  - 一次都不许从服务端漏出口令的代价写在启动日志里：放开"看"之后，同网段谁能连上谁就看得见那几台的
    型号、负载与档位；他换不走凭据、也借不到这台机器去连别人。
- `GET /api/devices` 读 `devices.json`（首次没有就按内置默认生成一份）；`PUT /api/devices` 写回，
  先写 `.tmp` 再改名，避免中途崩溃留下半个 JSON。
- 页面一打开就从文件起列表；之后任何编辑（改名 / 换档 / 电源 / 系统 / 地址 / 用户名 / 增删 / 排序）
  去抖 400 ms 写回一次，弹窗里那行"来源"会显示最近写入时间。
- **分区表单独一个文件**：`GET /api/zones` 读、`PUT /api/zones` 写 `zones.json`（同样先写 `.tmp` 再改名），
  字段三个 `{ key, cn, at: [x, z] }`。`key` 是内部标识（设备的 `zone` 指的就是它），**改名不动 key**，
  所以"改分区名"不会把已经钉在这个区里的设备弄丢。文件还不存在时服务端回 `{ list: null }`，
  页面保持内置的默认摆位 —— "默认四个区摆在哪"是页面的事，两处各写一份必然走散；改一次才生成这个文件。
- **落盘字段八个**：`name / tier / zone / power / os / host / user / pass`。
  `zone` 是 2026-09-23 加分区时补的第 8 格，**空串 = 按档位自动落区**（算力=itx/matx/atx/eatx、终端=laptop、
  储存=nas、网络=switch/router），填了就是手动钉住。服务端只校验它"长得像 key"（`[a-z0-9_-]{1,24}`），
  到底有没有这个区由页面按 `zones.json` 自己判：这里写死一份名单的话，页面里新建的分区一落盘就被清成空串。
  **`pass` 是明文**——
  2026-09-23 你明确说"账号密码可以先写进配置文件"，所以收。这条推翻了派单里
  "凭据不要出现在任何产物里"那一句（只对这个本地文件生效），代价写清楚：
  **`devices.json` 从此是敏感文件** —— 不要拷进仓库、不要进分享包、不要贴进群或截图。
  现在清单里是八台：笔记本 / ITX / mATX / ATX / E-ATX / NAS / 交换机 / 路由器。
  **2026-09-23 晚按用户给的四台机器填了前四行**（笔记本 / ITX / mATX / ATX，
  分别是"当前这台 + 算力集群三台"），后四台（E-ATX / NAS / 交换机 / 路由器）
  仍是纯装饰：地址空着 = 继续走模拟，一块屏幕都不会因为少了它们而空 —— 它们本来就是"八台一排"的构图。
  档位对得上分区：itx/matx/atx → 算力集群，laptop → 终端设备区，所以"算力集群三台 + 终端一台"
  摆出来正好是那四台机器。
  ⚠ **这份文档不抄那四台的地址与用户名**（虽然它们只是内网地址）：仓库是公开的，
  而"哪台机器、什么账号、哪台不设密码"拼起来就是一张可直接照着敲的目标清单。
  地址、用户名、明文口令只存在于本机的 `devices.json`（已 gitignore）；
  仓库里那份 `devices.example.json` 凭据全空。
  前三台的密码是**空串**（Windows 那几台本来就不设密码），ATX 那台（142 推理机）是明文口令。
- **`probe.log`**：每次 `/api/probe` 追加一行 `时间  OK|FAIL  主机  错误首行`，
  **不记用户名与口令**。有它在场，"有没有人偷偷连过某台机器"是可以查证的，不用凭谁的记忆说。
  截至 2026-09-23 下午，该文件三行：一行 `FAIL 127.0.0.1`（我自测打本机 sshd，认证失败），
  两行 `OK`（目标是 142，见 §八）。**除这两次之外没有连过任何机器。**
- 读文件时做归一：档位不在表里退回 mATX、字符串截断、布尔归一、非对象项丢弃——手改坏 JSON 不会把页面搞崩，
  最坏情况回落到内置默认并在来源行标出。
- **设置也是文件（2026-09-23：从"只活在浏览器里"改成文件是真源）**：`GET/PUT /api/settings` ↔ `settings.json`。
  起因是"部署成看板后要能直接调参数，不用去碰那台机器的浏览器"。方向**双向**：
  启动先读文件（文件在就是权威，覆盖浏览器里的旧存档）、页面里拖滑块/点开关 400 ms 去抖写回、
  **每 5 秒再读一次** —— 所以直接改 json，墙上几秒后自己就变，不用刷新。
  `localStorage`（`hm.pulse.v1` / `hm.mon.v1`）降级成"服务起着但接口读失败"时的兜底；
  **看板宽度 `hm.perf.width2` 故意不进这个文件**——那是"一人一屏"的排版偏好，不是看板的展示参数，
  换台机器/换个人看就该各是各的默认值。弹窗标题那行会写明当前是"存 settings.json"还是"只在浏览器里"。
  三组、键名跟代码里一模一样（不另起一套中文键，多一层映射就多一处会走散的地方）：

  | 组 | 键 |
  |---|---|
  | `pulse` | `enabled`（总开关）· `pulseStartBrightness` · `pulseEndBrightness` · `upParticleBrightness` · `travelK` |
  | `ground` | `rippleEnabled` · `rippleHeight` · `rippleThickness` · `rippleBrightness` · `rainEnabled` · `rainBrightness` · `dotSeg` · `dotSizeMm` + 三档波速/节拍六键（`rippleSpeedIdle/Active/Alert` · `rippleIntervalIdle/Active/Alert`，见本文「地面与雨」一节） |
  | `monitor` | `intervalMs`（重画节拍）· `probeEveryMs`（抓帧间隔，2026-09-24 加） |

  **范围不在服务端再抄一份**：那张真表是页面的 `PULSE_LIMITS` / `MON_LIMITS`，服务端只保"形状对、类型对"
  （布尔就是布尔、数字必须有限；不认得的键直接丢）。写了越界的值 → 页面钳回 → 把钳过的结果**回写文件**，
  于是文件里躺的永远是"实际生效值"，人改文件也能一眼看出自己写的值有没有被收掉。
  文件顶层 `_说明` 那句人话由服务端负责：磁盘上有就原样保留（人改过那句话就照他改的），没有就补一份默认的，
  排在文件最上面。文件整份删掉 → 下次打开页面按默认重新生成一份（带 `_说明`）；文件被手改残（一个认得的键都没有）
  → 页面把生效值写回去，坏文件不该一直坏着。
  `settings.json` 已进 `.gitignore`（跟 `zones.json` 同理：默认值写在 `src/model.mjs` 里，这份是"改过"的版本；
  进仓库的话本地拖一次滑块就把工作区弄脏）。
- 「连不上服务就退回 `localStorage`、来源行写明只在内存」这条路现在只在**服务起着但接口失败**时走得到：
  监控墙这一页已经不能靠 `file://` 打开了（见本节开头），所以"没服务"这一档不再是"双击打开"。
- 依赖只有两个，都写在本目录 `package.json`：`ssh2 ^1.17.0`（探测）+ `three 0.170.0`（让 node 能 import
  两个几何模块做校验；页面走 CDN importmap，跟这个依赖无关）。`node_modules/` 已进 `.gitignore`。
  立项时是从 `00-暂存\素材` 整份拷过来的，装前装后工作区根的 `package.json` / `pnpm-lock.yaml`
  md5 与 `node_modules` 条目数完全一致 —— 当初装 ssh2 没有顺手改写外层任何东西。

## 八、数据来源分流 + 脚下脉冲

- **分流只有一条判据**：`连接地址 + 用户名` 填了 = 这台走 SSH；缺任一个 = 模拟。
  **密码不再是判据**（2026-09-23 改）：办公那几台 Windows 是"账号 user、不设密码"，
  空口令是它们的正常配置，不是"没填全"。linux 那边口令不对就如实报失败（屏上标"抓不到"），不会假装成功。
  凭据会落盘（见 §七），所以**刷新后这台仍是"可采"态**，chip 会显示 `待抓，仍模拟`（红），
  点一下"连通性测试"就转成实测。之前"刷新后必须重输密码"的代价随明文落盘一起消掉了。

- **两套抓法，由清单里的"系统"那一格分流**（2026-09-23 加 Windows 分支）：
  - linux → 一条 sh 命令拼起来（`hostname` / `/etc/os-release` / `nproc` / `free` / `/proc/loadavg` /
    `df -B1 -P /` / `nvidia-smi`）。
  - win → Windows 的 OpenSSH 给的远端 shell 是 **cmd.exe**，带引号的 PowerShell 语句在 cmd 里会被折腾得
    不成样子；所以整段脚本按 UTF-16LE 编码成 base64、用 `-EncodedCommand` 递进去（命令行上只剩
    `A-Za-z0-9+/=`，引号地狱一次性绕开），数据取自 CIM（`Win32_OperatingSystem` / `Win32_Processor` /
    `Win32_LogicalDisk`）。两处细节不是装饰：`[Console]::OutputEncoding=[Text.Encoding]::UTF8`
    （不加的话"Microsoft Windows 10 企业版 LTSC"这行按本机代码页出来，到这边就是乱码）、
    `$ProgressPreference='SilentlyContinue'`（不加的话进度条会以 CLIXML 糊满 stderr）。
  - 两边输出同一套 `KEY=value` 行，由同一段解析变成 frame。Windows 首次要现起一个 PowerShell，
    实测 138 冷启动 2.7 s、195 1.8 s、Linux 那台 0.3 s —— 所以 **Windows 的超时上限是 25 s，linux 仍是 8 s**；
    整条链路的 8 s 一刀切会把 Windows 正常的连接掐掉。
  - **"忙不忙"这一格两种系统口径不同**：Windows 的 CIM 直接给占用率（`LoadPercentage`），
    linux 给的是 1 分钟负载均值（不直接是占用率）。frame 里因此有两条：`cpuPct`（只有 Windows 有）
    与 `load1`（Windows 那个是"占用率折成的等效负载"，让页面那条老公式照样成立）。
    页面统一走 `framePct(f)`：有 `cpuPct` 就用它，否则 `load1 / cores × 100`。
    看板总使用率、脚下游走分级、连通性测试那行字("CPU 占用" / "1 分钟负载")全从这一个函数取，不各算各的。

- 走实测的那台，一帧快照能给的：主机名 / 系统 / **核数** / 忙不忙 / **内存总量与已用** / 根分区容量 / 有没有卡（`nvidia-smi`）。
  给不了的：**各核分布、频率、温度、磁盘与网络的读写速率**——一次快照没有速率。
  所以 `hwOf(d)` 只把核数 / 内存容量 / 显卡张数换成实测值，其余继续模拟，并且**每一节的抬头挂一枚 chip 标明出处**：
  `整机占用 实测 · 分布分摊`、`容量 实测`、`一帧实测`、`未抓到 GPU`（红）、`模拟（快照无速率）`、
  `抓不到，仍模拟`（红）、`模拟`。红标出现即代表这台确实在走 SSH 分支且没拿到数据。
  - **2026-09-24 订正（上面那两句已按实况改版，逐字账在这里）**：探针后来加了 1 秒两采样，
    **磁盘与网络的读写速率已经是实测**（`DRATE` / `NETRATE`）；**各核分布也是实测**
    （Windows 走 `Win32_PerfFormattedData_Counters_ProcessorInformation` 的每逻辑处理器实例，
    Linux 走 `/proc/stat` 两次采样），所以"分布分摊"这种"实测的总数摊到模拟的各核"的说法早已不成立。
    出处标记（`srcTag`）现在只剩四个词：**模拟 / 实测 / 抓不到 / 待抓**，
    上面那一长串 chip 名是历史文案，码里已经没有了。
    **还没给不了的只有两项，而且是系统层给的**：Windows 取不到实时频率与 CPU 温度（看板显示"—"），Linux 两个都有。
  - **"核"与"线程"这两个词现在是分开的**（2026-09-24，用户指出"点开之后还是显示线程，不是核心"）：
    探针多输出两行 —— `PCORE`＝每个逻辑处理器属于哪个物理核（Windows 取 `GetSystemCpuSetInformation` 的
    `CoreIndex`，Linux 取 `lscpu -p=CORE,SOCKET`）、`PCLS`＝每个逻辑处理器是 P 还是 E（只有混合架构才有，
    Linux 不报）。看板 `liveCpu()` 按 `coreMap` 把逻辑处理器并成**一物理核一张卡**，
    抬头写"N 核 · M 线程"，卡题写"核 3"（没有映射时才退回"逻辑处理器 3"）。
    `serve.mjs` 里那两行过一道 `aligned()` 长度闸：**长度跟 `perCore` 不等就整段判 `null`**，
    绝不按下标猜 —— 猜错的话会把两个不同核并成一张卡，那种错在屏上看不出来。
- 传输层是 `ssh2`，已装在 `素材\node_modules`（`^1.17.0`）。`serve.mjs` 用 `await import("ssh2")`，
  换机器没装时每条请求明确回 `本机未安装 ssh2`，所以"抓不到 → 标红"这条分支不碰任何真实机器也能验。
  `/api/probe` 只有主人能调（2026-09-24 起看的是来源地址在不在 `HM_OWNER` 里，不再看 `Origin`；见上文「两扇门」），
  用户名/口令不回显、不进日志，
  只有"时间 + 目标主机 + 成败 + 错误首行"进 `probe.log`。
  **抓不到也回 200**（2026-09-23 改，原来是 502）：HTTP 这一层是成功的（请求到了、连也试过了），
  成败在响应体的 `ok` 那一格上。原来那个 502 会让浏览器控制台替**每一台抓不到的机器**记一条红色错误，
  而"打开页面时对每台填了地址的机器各抓一帧"（见下）本来是常规动作 —— 看板机一开机就是几行红的，
  看着像坏了。（业务层的 403 来源 / 405 方法 / 400 请求体还照旧是错误码。）
- **一条硬约束被这次改动带出来，记死**：`probe()` 里一个笔误（`ssh2` 写成未定义的名字）在 Promise 里抛出，
  会变成 unhandled rejection，**把整个 serve 进程带走**，页面只看到一个断掉的连接（http=000）。
  路由现在包了 try/catch：任何一次探测失败只回一条 `{ ok: false, error }`，服务不倒。
- **第 5 项"拿 142 真实抓一帧"已开并已跑通（2026-09-23 下午，用户口头放行"所以你可以开"）**。
  两次实测都从页面里点"连通性测试"走完整链路（浏览器 → `/api/probe` → ssh2 → 142 → 一帧 → 看板），
  弹窗回读：`主机名 infer-142`、`系统 Ubuntu 24.04.4 LTS`、`核心数 12 核`、`1 分钟负载 0.15 / 0.02`、
  `内存 5.8 / 15.5 GB`、`磁盘（根分区）61% 已用`、`GPU 0% · 显存 21943/22528 MB · 53°C`。
  `probe.log` 里对应两行 `OK`（目标是 142，地址只存在于 `devices.json`，不抄进这份文档；
  日志本身只有时间/主机/成败，没有用户名与口令）。
  **交叉核对**：这台抓到帧后负载 = 0.02/12 ≈ 0%，于是它的分级钉在 `IDLE 0%`、脚下是绿色慢脉冲，
  而旁边四台模拟机在 30~77% 之间游走 —— 说明分级读的是真数、不是随机数。
  用户先前自己点过一次（比日志还早），那次也通。
- **四台一起抓（2026-09-23 晚，隔离端口 + 只读探针）**：清单里那四台各抓一帧，
  ITX（win，2.7 s）、mATX（win，1.8 s）、ATX（linux，0.3 s）三台 `OK`，
  笔记本那台 `FAIL · All configured authentication methods failed` —— 它没设密码、密钥还没生成完，
  用户说的"密钥是否可用"目前的答案就是**这条链路暂时接不了**（`serve.mjs` 只支持口令登录）。
  三台的实测值都上了看板：`SSH实测` 标签 + 脚下游走分级读的是真数
  （ITX 74% → `ALERT`、mATX 1% → `IDLE`、ATX 26% → `IDLE`）。
  桌面 Windows 那台还带回一张卡（`2048 MB`、`nvidia-smi` 通），说明 Windows 分支连 GPU 也一并抓到了。
  页面控制台全程干净（这也是上面那条"抓不到回 200"的由来）。

**采集频率**（设置 → 采集频率；这一格原来叫"性能监控"，2026-09-23 改名。**2026-09-24 起这一格里是两拍**：
重画节拍 + 抓帧间隔，两条滑杆各管各的 —— 原来只有一条，用户看到的"默认每 3 秒更新但数值纹丝不动"就是这么来的：
那一拍只重画，真机的帧根本没人再去抓。）

**第一拍 · 重画节拍 `MONITOR_SETTINGS.intervalMs`**：一个 `setInterval` 同时驱动两处 —— 右侧看板的数值推进、
每台设备的"负载 → 分级"判定。放同一个定时器是刻意的：否则会出现面板已换新、脚下脉冲还挂在旧状态。
滑杆 **200~60000 ms**（步进 100，**默认 3000**；2026-09-23 按用户要求从 800 改成 3 s，
2026-09-24 把上限从 5000 放开到 60000 —— 看板挂墙上没人愿意 3 秒闪一次，而原来 5 s 封顶根本调不到"十秒一更新"），
改完立刻重启定时器并写回 `settings.json` 的 `monitor.intervalMs`（没起本地服务时才退回落 `localStorage["hm.mon.v1"]`）。
**滑杆右边那行字只报"每 3000 ms 1 次"**：原来还算了一个 `1000/v`，出来的"1.2 次/秒 / 1.3 次/秒"
是小数，读着像算错了 —— 步进 100 ms 本来就不可能整除出整数次数，所以那一半删掉。

**第二拍 · 抓帧间隔 `MONITOR_SETTINGS.probeEveryMs`（2026-09-24 加；滑杆 3~600 s，步进 1 s，默认 15 s）**：
一次快照要在远端跑好几条命令（Windows 那几台还得现起一个 PowerShell，实测 1.4~28 s），
所以它**绝不跟第一拍同频** —— 3 秒一轮等于让同事的机器连轴转地开进程。
**2026-09-24 晚这一拍整条搬进 `serve.mjs`**（原来是页面里的 `setInterval` + `probeRound()`，那一版已作废）。
搬的理由不是洁癖：要放开"看"就得让口令不出看板机 ⇒ 观众拿不到 `user`，本来也就发不出探针；
而原来页面一关、墙上那几台的数就再也不动。搬完后**所有页面都关掉也照抓**，页面只每 2 s 取一趟缓存。
- **服务端那一轮是怎么跑的**（`runRound()`）：按名册顺序**串行**抓，每台之间歇 `ROUND_GAP_MS = 1200` ms
  （别同一瞬间捅四台），跳过 `hidden` / 没填地址 / 没填用户名的；一轮跑完才回 `settings.json` 读那一格
  `probeEveryMs` 排下一轮（钳在 `EVERY_FLOOR=3 s` ~ `EVERY_CEIL=10 min`，手改文件写 10 ms 也不会变成 SSH 轰炸机）。
  开头那行 `if (roundRunning) return;` 是刻意有的：一轮本身 20~45 s，"催一轮"连点两下不该让真机负载翻倍
  （2026-09-24 18:09 实测踩过：手勾那一轮还没跑完又起了一轮）。
  帧按 host 存在内存那张 `frames` Map 里，**故意不落盘** —— 里面装的是别人的负载，重启后重新抓一帧就是。
  所以这一格的语义仍是"**两轮之间歇多久**"（从上一轮抓完那一刻起算），不是"每台多久抓一次"：
  本机实测四台里三台在线（ITX 27.8 s / mATX 13.3 s / ATX(linux) 1.4 s），**一整轮 ≈ 45 s**，
  于是名册末尾那台的帧最旧能到 ~50 s。这个数是"抓帧间隔 + 一轮耗时"，不是 bug ——
  想快只能减机器数或让 Windows 那两台别冷启动 PowerShell。
- `GET /api/frames` 是页面唯一的取数口（观众也能读）：除了帧，还回一格 `rounds`
  （第几轮 / 在不在跑 / 起止时刻 / `everyMs` / 下一轮还剩多久），所以"这一拍到底有没有在跑"是一条 HTTP
  就能问出来的，不必盯着屏幕等。页面按 `frame.at` 比对才更新，同一帧反复取不会重画。
- ⚠ **整区关闭（`zones.json` 的 `off`）与 `power:false` 这两条不在服务端复算**：那份判据长在页面
  （`model.mjs` 对着 `zones.json` 查），这里再抄一份就是两个真源、早晚走散。代价是"关掉一个区"之后
  服务端还会照着抓那一区的机器，每轮一次 SSH；放出来那一刻它已经有现成的数，不用等下一轮。
- ⚠ **这一格必须同时列在 `serve.mjs` 的 `SET_SHAPE.monitor` 里**（2026-09-24 舞台实测抓到的真缺陷）：
  `normalizeSettings` 只认表上列出的键，少列一格 = 页面每写一次设置就把文件里那一格丢掉，而屏上那根滑杆照样会动。
  当时 `monitor` 只列了 `intervalMs`，症状是服务端永远按默认 15 s 歇 —— 要等它自己转轮次才现形。
  搬进服务端之前这格只活在浏览器内存里，所以掉了也没人知道。今天起它由 `verify-access.mjs` 钉住（键名表逐个对）。
- **同一台只允许一帧在飞**（`probeFlights` 那张 Map 认设备 id，仍在页面这一侧）：双击补抓和"连通性测试"
  同时命中一台时不会抓两遍，第二个人拿到的是同一个 Promise。
- **抓到帧之前，这台在"脚下分级"那一层压根没有档位**：`stepLoads` 对填了地址但还没帧的机器把 `pct` 留 `null`，
  于是涟漪/脉冲都不为它起（2026-09-24 的订正，见下那条"没数就不编数"）。
  那一帧回来之前，脚牌上写的是 `● 待抓`（或 `● 抓不到`），不是随机游走。

**抓帧的入口**（2026-09-24 晚搬到服务端之后重列了一遍；更早那版"只有两个入口、没有自动轮询这条线"早已作废）：
1. **服务端自己转**：`node serve.mjs` 一起来就立刻跑第一轮，之后每 `probeEveryMs` 一轮，**跟有没有人开着页面无关**。
   抓到的自己爬上看板，抓不到的只标红、不影响别的（`/api/probe` 抓不到也回 200，见上）。
2. **主人催一轮**：`POST /api/round` = 打断排期立刻开一轮，回的是 `rounds` 那一格；页面按了不直接拿数，
   仍从 `/api/frames` 的缓存里读 —— 这一头不另发 SSH。自测用它，不必干等下一轮。
3. **双击补抓**（`probeIfFreshless`，**只有主人这条动作存在**）：点开一台有地址但**一帧都还没有**的机器，
   当场按台抓一次（走 `/api/probe`），不等服务端那一轮 —— 原来"首次进入双击设备一直加载不出数据、
   关掉页面重开才有"的根因就是这一段空窗。已经有帧的不抓：双击不该变成"每点一下敲一次同事的机器"。
   观众点这一台直接返回（按钮都不给他，`/api/probe` 他调了也是 403）。
4. **手动**：设置弹窗里的"连通性测试"（含失败后重试），同样是主人限定。

**哪些数值是真会动的**（"是没有动态指标吗"这一问的答案，按当前探针）：CPU 总占用 + 每核占用、
内存已用、Swap、磁盘各卷读写速率与网络收发速率（探针内部那 1 秒两次采样算的）、GPU 利用率/显存/温度/风扇/功耗、
linux 的实时频率与各核频率、CPU 温度（**只有 linux 有**：Windows 的 CIM 不给实时频率也不给温度，看板显示"—"）。
一帧快照给不了的只有：磁盘/网络的**累计历史**（只有当前速率）、以及 Windows 侧的频率与温度。

**换到毫米口径时我改了三个量，每个都有理由**：

1. **半径按"机器本体"算，不按整套桌面**：桌面组合里显示器 + 键鼠把包围盒摊到 860 mm 宽，
   拿它当 footprint 的话一圈能罩到邻居家脚下（台间距才 2140 mm）。所以 `rebuild()` 里
   取 `getObjectByName('chassis') || getObjectByName('laptop') || model` 再量一次，
   NAS / 交换机 / 路由器这三档整个模型就是本体。mATX 那一档实测 footprint 半径 174 mm × 18 → 环最远 3.1 m。
   ⚠ 2026-09-24 你把 `travelK` 定到 18 之后，**环确实会越过台间距铺到邻机那一片** —— 这是你要的效果
   （"直径至少 3 倍"），不是漏算；这条 footprint 约定的作用变成"别让显示器和键鼠把半径撑大"。
2. **向上粒子默认压到 0.22**：参考那套是"相机 48 单位看 6 单位的机器"，粒子在屏上稀疏；
   这里全景离地十几米，一束 60 粒挤在几个像素宽里，`AdditiveBlending` 直接**饱和成白柱、颜色全丢**。
   滑杆上限仍是 1，要更亮自己拖。
3. **没带 UnrealBloomPass**：派单禁 `three/examples/`，所以参考里那层光晕糊不出来，
   整体比参考暗一档是预期、不是掉效果。要真做辉光得先解掉那条红线（或自带一份 bloom）。
   贴图为补偿全部走白色程序化渐变（`softDotTexture` 圆柔光 / `tailTexture` 横向拖尾），
   颜色由 `material.color` 按分级染，三档共用同两张图 —— 运行时 canvas，**不是外部素材**。

**分级阈值（`STATES` 里那三个 `max`，改一处即可、别处不动）**：`≤35% 空闲 / 35~70% 活跃 / >70% 高负载`。
**这个百分数是什么 —— 2026-09-24 深夜他裁的口径 B**：`pct = max(CPU 占用, GPU 利用率)`，再叠一条内存的例外：

- CPU 那一维：Windows 取 CIM 的 `LoadPercentage`，linux 探针把刚采到的每逻辑核占用求平均；
- GPU 那一维：`f.gpus[].util` 逐张取最大（142 两张卡走这里），没有 `f.gpus` 时吃老字段 `f.gpu.util`（Windows 出这个）；
- **缺的那一维整条退出，绝不拿 0 顶位**：无 nvidia-smi 的机器（138 的核显报 0 是它真报了 0，195 那种是"没有这一维"）、
  GPU 只有型号没指标的（lspci/WMI 那条路），一律不参与 max。"没数据"伪装成"这一维很闲"就是新的假绿；
- 内存**不并进 max**，只在 `memPct ≥ 92 %` 且当前判为"空闲"时把它抬到"活跃"，**永远抬不到"高负载"**。
  理由：常驻高内存是常态不是事件（16 G 的笔记本日常就挂八九十），并进 max 会把那台钉成永久黄/红，
  墙反而看不出"变化"——而变化检测就是这个看板存在的理由。
- 没帧的道具 = 本地随机游走（每台相位不同，避免五台同色同拍）；填了地址但一帧没抓到 = 没有档位（不编）。

落点只有两处：`src/ground.mjs` 的 `realLoadOf`（读帧算 max）与 `src/model.mjs` 的 `gradeOf`（定档 + 内存抬档）。
**换档那一刻名字那行标注会跟着变颜色**（绿/黄/红 + `● 高负载 74%`），所以不用盯着脚下也能核对分级没算错。
仪器那一格：`__hm().loadState()` 把"屏上那一档"和"按帧里那三样该判成什么"并排报出来（道具两边必然不同，那是游走不是实测）。
闸：`verify-load.mjs`（已进 `npm run check`）截这三段原文跑 12 例，含门槛含等号（92.0 抬 / 91.9 不抬）、
缺 GPU 维、只有 GPU 没 CPU、内存字段缺、没帧五种边界；变异实验验过它不是空转（把 GPU 那一维摘掉 → 3 条翻红，`>=` 改 `>` → 1 条翻红）。

**实测读数（八台全开、稳态）**：屏上恒有 14~17 个环 + 14~17 束上飘（`scene` 里 Points 30~34 个），
粒子总数 1.0~1.6 万，`updatePulses` 的 **CPU 提交时间 ≈ 1.2~2.3 ms/帧**（约 0.086 ms/千粒）。
2026-09-24 做了单变量变异实验（`settings.json` 里只改 `travelK`，同一页面同一场次来回切）：
**6 → 4.9~5.5 ms/帧**（16~17 环、13580~14440 粒）、**18 → 5.8~6.2 ms/帧**（20 环、16960 粒）。
所以放大半径这一刀的量级是 **+0.7~1 ms/帧**，不是"3 倍贵 9 倍"那种关系（环数只多了 3 个，粒子数按台×档位数算）。
⚠ 上面那条 1.2~2.3 ms 是 2026-09-23 夜另一场次测的，**跨场次不可比**（这台机器白天和半夜不是一个负载）——
要判"有没有回归"只能像这样在同一分钟内把两个值来回切三次取中位数。
连推 30 s 队列不增长（`排队` 全 0 或瞬时 1~2，即"正在三连发中途"）——**没有泄漏**。
⚠ 这只是 CPU 侧，GPU 的填充/合成开销没量（后台标签页量它必然出假数），**帧率要开人眼**。
自检钩子 `__hm().pulseRun(n)` 手推 n 帧（×50 ms）并回投上面这些数；
它的时钟基准取 `max(上次探针, clock.elapsedTime)` 再往前推，**跨次调用保持单调**——
上一版每次从 0 起，把延迟队列甩到"未来"、虚拟时钟永远追不上，读数假 stuck（我差点把它记成 bug）。

**参考里没取的部分**：屏幕跟着闪那一下（你说"仅脉冲"）、`EffectComposer` 那套后期、

### 地面与雨（2026-09-23 融合，规格 = 仓库里 `docs/参考-涟漪地面/` 那三份 + `docs/参考-数字雨/`）

原来的 `GridHelper(24000, 96)` **整张删掉**，换成参考里那张点阵涟漪地形（`RippleTerrain`）：
涟漪开着时它做两件事（2026-09-24 起）——① 整张地按两列正弦慢慢起伏（`BREATH` 那层底波，不需要谁踢一脚）；
② 每台开机设备按自己负载档位的间隔从脚下起一圈环向外荡，环与环可叠加。涟漪关着时点阵原地静止
（你裁的是"关掉涟漪＝回到静止点阵"，没有把 GridHelper 找回来）。
公式一个字没改（高斯包络 `exp(-d²/(t²·100))`、`sin(d·0.5)`、寿命衰减 `1-age/4`、距离衰减 `exp(-r·0.008)`、
`wave` 乘 amplitude；高度累加 `wave·height`，颜色累加 `色·|wave|·brightness·0.9`）。

**两个换算比例，不是一个**（这条是这次融合最容易踩的坑，记死）：

| 常量 | 值 | 为什么是这个数 |
|---|---|---|
| `GROUND_S` | 80 mm / 参考单位 | 按**地图多大**换：参考 300 单位一张地 → 24000 mm，正好是原 GridHelper 的边长。几何仍建在参考单位里（`PlaneGeometry(300,300,180,180)`）再整张 `mesh.scale` 放大，于是公式里 0.5/0.008/100/150/4.0 全部原样成立。点径是**材质尺寸**、不吃 `mesh.scale`（three 的 point size 是世界单位），所以单独乘一次：`0.7×80 = 56 mm` |
| `RAIN_S` | 400 mm / 参考单位 | 按**相机离背景多远**换，跟地图多大无关：参考相机离雨幕约 140 单位，我们全景时离雨壳约 56000 mm → 1 单位 = 400 mm（正好 `GROUND_S×5`）。字号 `1.8×400 = 720 mm`、下落 `3~8×400 = 1200~3200 mm/s`、雨柱高 `80×400 = 32000 mm`、光斑上升 `0.8×400 = 320 mm/s`，全按这个比例走，看上去的**大小和速度**才跟参考一致 |

**雨壳半径 `40000~54000 mm`**：参考把雨布在 −Z 一面幕布上，因为它的相机不绕；我们是轨道相机，
转过去那面字墙就穿帮，所以按对齐结论改成环绕地图的圆柱壳（800 滴 + 150 颗光斑，光斑仍是
`sizeAttenuation:false` 的屏幕空间 2.5 px）。**壳必须整个套在相机外面** —— 相机拉距硬上限 30000，

**触发接线（2026-09-24 脱钩）**：`STATES` 三档各带一个 `amplitude`（IDLE 0.6 / ACTIVE 0.85 / ALERT 1.2，参考原值）。

**底波（`BREATH`）**：整张地按两列可分离正弦慢慢起伏（`amp 0.3` / `glow 1.6` / `k1 0.055` / `k2 0.115` /
`s1 0.55` / `s2 0.85`，都是参考单位与秒）。可分离是为了省：每帧只算 `4×(dotSeg+1)` 次 `sin` 当行列因子，
3.2 万顶点里只做乘法。它跟涟漪共用一颗开关（关了地面彻底静止），高度吃 `rippleHeight`、明暗吃
`rippleBrightness`，**没有往 `settings.json` 里加新键**；辉光只是把待机色整体抬起，不引入新色相。

**点阵密度（`dotSeg`，2026-09-24 加）**：地面每边段数，顶点 `(dotSeg+1)²`，点距 `24000/dotSeg` mm。
以前这个数是写死的常量 `GROUND_SEG = 180`，现在常量删了、唯一真源是 `PULSE_SETTINGS.dotSeg`。
- **它只换采样分辨率**：涟漪环与底波的公式（`0.5 / 0.008 / 100 / 150 / BREATH` 的 k）全在参考单位里，
  一个数都不跟着 seg 走。正对照（同一场次、清掉所有环之后第一帧）：180 段 `起伏mm [-10,+12]`、
  360 段 `[-12,+11]`，`隆起点数 / 顶点` = 0.724 vs 0.690 —— 高度与波形没变，只是点更碎。
- **两颗旋钮只有 `RippleTerrain.syncDots()` 一处落地**：读设置 → `clampv` 收进合法范围 → 点径不一样就改
  `material.size`（一个数，不涉几何）、段数不一样才造新 `PlaneGeometry` 并 `dispose()` 旧的。三条来路（拖滑杆 /
  5 秒读 `settings.json` / 启动恢复）都走它，所以 `settingsToFile` 与 `applySettings` 里不需要为它们写特例。
  `syncDots()` 写在 `update()` 的**第一行**（取 `positions` 之前），换档后那些数组才是新几何的。
- 拖滑杆时 `input` 事件每像素都触发，但重建一帧最多一次（值变了才重建）——这就是把换算放进帧内而不是放进事件里的原因。
- **点径不跟着段数走**（它是材质上的一个世界毫米数，`PlaneGeometry` 的密度动不着它）：360 段点距 67 mm 时 56 mm 的点
  几乎手拉手，所以"密"和"小"要一起调——用户 2026-09-24 把默认定成 320 段（75 mm）之后紧接着就问"点可以更小么"，
  加这颗正是为了让他不用在"密"和"糊"之间二选一。点是加法混合，同样密度下点径越小整片越暗，反过来嫌糊就先把点径往回拉。
- 上限钉在 360 段是**成本**给的（13 ms/帧已经占掉 60 Hz 预算的四分之一），不是"点会重叠"给的——那条我原先的判断
  被实测否掉了：360 段 16 环常态下 `起伏mm [-60,+57]`、`隆起点数 98152`，环带仍然分得清。

厚度没变就不重建；② 高斯包络在 `|d| > 26.3×thickness` 时已小于千分之一 → 按行带剔除
